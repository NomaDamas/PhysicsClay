# PhysicsClay v1: physical, watchful, open (contract between the v1 workstreams)

The hackathon build (UX 2.0 and UX 3) proved the interaction model: say, point and show, and the robot proposes
while you correct. It also cut three corners that an open-source robotics project cannot keep:

1. **No physics.** The robot is posed by IK (`mj_forward` only, no `mj_step`). A picked object is teleported to the hand
   (mocap), so nothing slips, falls, collides or weighs anything. The recorded data cannot teach a real robot.
2. **The person is only a pointer.** The robot sees where you point and whether your hand is open. It does not
   understand what you are *doing* (welding, squatting, reaching for a tool), so it cannot work with you, coach you,
   or learn a technique by watching.
3. **Trajectories are 2D.** A drawn path is a stroke projected onto the table plus a fixed hover height. There is no
   height, wrist orientation, speed, force or tolerance, and no good way to author those in 3D.

v1 fixes all three, makes everything a dataset, and packages it as an open-source project people can install,
extend and trust. The principles stay the same. Language is coarse and the robot proposes. You fix only what is
wrong, by showing, pointing, drawing (in VR if you have it) or talking.

## P0 Physics (`pps/physics.py`, `pps/world/*`, `pps/robot_runtime.py`, `pps/tasks.py`)

**Physics is the default. `PC_PHYSICS=0` (or `--kinematic`) keeps the old kinematic mode as a fallback.**

* **Control loop.** IK stays the *planner*. It solves on its own `mink.Configuration` (a copy of the model) and produces
  the desired joint positions `q_des`. The *plant* is `mujoco.MjData` stepped with `mj_step` at the model timestep
  (2 ms) for `n_sub = round(dt / timestep)` substeps per server tick. The plant tracks `q_des` with:
  * position actuators (`<position kp=… kv=…>`, or the model's own actuators when it has them), or
  * joint-space PD as `qfrc_applied` when a model has no usable actuators (`ctrl_mode: "pd"`).

  Gains and effort limits come from the profile, with sensible defaults per kind.
* **Objects** are free bodies (`<freejoint/>`) with mass, inertia and friction (`condim=4`, torsional friction) instead
  of mocap. Names stay `obj_<name>` (movable) and `obs_<name>` (fixed, no joint). Tasks read poses from `data.xpos` /
  `data.xquat` of the body. Every place that used `mocap_pos[obj]` goes through one helper.
* **Grasping is by contact.**
  * Grippers have real finger joints and actuators: Panda fingers, Robotiq 2F-85 on UR5e (from MuJoCo Menagerie if it
    is present, otherwise a simple parallel-jaw gripper built in XML), xArm gripper, ALOHA fingers.
  * Humanoid hands without fingers get a simple two-pad parallel gripper on the palm site.
  * A grasp succeeds only when both pads touch the object and it lifts with the hand. Slip is detected: the object
    lags the hand or falls, and the task fails honestly ("it slipped").
* **Humanoids.**
  * Manipulation runs with the pelvis welded (`base: "legged"` and `physics_base: "fixed"`). The legs are
    PD-held at the stand keyframe.
  * Dynamic walking is out of scope (it needs a learned locomotion policy). This is stated in the profile note and
    the docs.
* **Compliance.** `impedance` mode: lower stiffness, an effort cap and a force limit at the end effector, used for
  wiping, pressing and anything that touches a person. A per-task `force` (N) is tracked along the approach axis by a
  simple admittance outer loop on `q_des`.
* **State.** Physics keeps the existing `state.world` / `state.task` keys. It adds:
  ```json
  "physics": {"mode": "dynamic"|"kinematic", "dt": 0.002, "rtf": 1.0,
              "grasp": {"right": "red_cup"|null, ...}, "ee_force": {"right": [fx, fy, fz]},
              "contacts": [{"a": "right_pad", "b": "obj_red_cup", "f": 3.2}], "params": {...}}
  ```
* **Message.** `{type: "physics", op: "set", params: {friction_scale, mass_scale, damping_scale, kp_scale, latency_ms,
  gravity}}` changes the plant parameters at run time (used by P6 randomization and calibration). `op: "reset"`
  restores the defaults.
* **Done when** the full self test passes in dynamic mode, and every robot except experimental ones does a real
  contact pick & place. A new physics check proves:
  * an object dropped from 10 cm lands and rests;
  * a pick with gripper force 0 fails as a slip;
  * a heavy object (`mass_scale` 20) is refused or dropped honestly;
  * impedance mode keeps the end-effector force under its limit while pressing on the table.

## P1 Datasets (`pps/data/`)

* **Format.** **LeRobot v2** dataset layout under `datasets/<name>/`:
  * `meta/info.json`, `meta/episodes.jsonl`, `meta/tasks.jsonl`, `meta/stats.json`;
  * `data/chunk-000/episode_XXXXXX.parquet`;
  * `videos/chunk-000/observation.images.<cam>/episode_XXXXXX.mp4`.

  It needs `pyarrow` (add it to the deps) and ffmpeg. Each frame records, at a fixed control rate (default 30 Hz):
  * `observation.state`: joint positions and gripper;
  * `action`: `q_des` and gripper command;
  * `observation.images.{front,wrist}`, rendered offscreen at 256×256;
  * `timestamp`, `frame_index`, `episode_index`, `task_index`;
  * `next.done` and `next.success`;
  * optional `observation.human.pose` (33×3 world landmarks, zeros when no person) and `observation.ee_force`.
* **Episodes.** An episode is one task, from start to done or failed. Language comes from the user's words, or a
  paraphrase by the agent. Failed episodes are kept and labelled.
* **Messages.**
  * `{type: "dataset", op: "start", name, auto: true}` records every task as an episode.
  * `op: "stop"` and `op: "discard_last"` end recording or drop the last episode.
  * `state.dataset = {recording, name, episodes, frames, last: {...}}`.
* **Generate.** `scripts/generate.py --seed <traj.json|task.json> --robots panda,ur5e --scenes table,kitchen --n 100
  --randomize objects,physics,lighting` replays one intent as many randomized episodes headlessly (pipeline A in
  `docs/ROADMAP_DATA.md`).
* **Loader check.** A test loads the parquet and video and checks shapes and stats without importing lerobot.
  When `lerobot` is installed, an optional check loads the dataset with `LeRobotDataset`.

## P2 Trajectories (`pps/traj.py`, `pps/features/traj.py`, `web/ui/traj.js`, `web/xr.js`)

* **The trajectory object** (one schema for drawn, VR, language, demonstrated and keyframed trajectories):
  ```json
  {"id": "t1", "role": "right", "frame": "world" | "object:<name>", "source": "draw|vr|language|demo|keyframes|skill",
   "label": "over the vase to the right of the bowl",
   "points": [{"p": [x, y, z], "q": [w, x, y, z] | null, "t": 0.0 | null, "grip": 0..1 | null,
               "speed": 0.1 | null, "force": 5.0 | null, "tol": 0.01 | null, "note": "slow here" | null}],
   "pattern": {"kind": "zigzag|circle|figure8", "amp": 0.004, "freq": 2.0, "axis": "normal"} | null,
   "check": {"ok": [true, ...], "why": "...", "duration": 4.2}}
  ```
  `frame: object:<name>` means the points are relative to that object, so the trajectory follows the object when it
  moves. That is how a demonstrated skill generalizes.
* **Compile.**
  * `pps/traj.py` densifies the trajectory: min-jerk timing from `speed`, slerp for `q` and the pattern
    superimposed.
  * It checks each point (reach, joint limits, collisions, zones, safety) and runs it through the P0 plant.
  * `follow_path` becomes a `traj` with `source: "draw"`, and the old messages keep working.
* **Messages.**
  * `{type: "traj", op: "set" | "propose" | "edit" | "run" | "clear", traj?, index?, point?}`.
  * `state.traj = {current, proposed, ok, why, running, i}`.
  * `propose` shows a ghost (a translucent end effector along the path) and needs confirmation, as in plan preview.
* **Authoring on the desktop** (`web/ui/traj.js`, 3D stage):
  * Language first: the agent tool `make_trajectory(description)` has the LLM write keypoints relative to objects
    with height, orientation, speed and force notes, and `pps/traj.py` turns them into a smooth, checked trajectory.
  * Edit with handles: drag a point on its plane, change height with the scroll wheel or Alt-drag, and rotate the
    wrist with a ring gizmo. Each point has speed and force chips.
  * Keyframes: drop 2–5 ghost grippers and they are connected automatically.
  * Voice edits: "higher there" and "slower near the vase" work through the agent.
* **VR / MR** (`web/xr.js`, WebXR, Meta Quest browser, over https on the LAN):
  * An "Enter VR" button appears when `navigator.xr` supports `immersive-vr` or `immersive-ar`.
  * Hand tracking (`hand-tracking` feature) or controllers. Pinch and drag draws a trajectory 1:1 in the air, and the
    pinch distance can map to speed.
  * Grab a ghost gripper to place a keyframe, then twist the wrist to set its orientation.
  * Passthrough (`immersive-ar`): the sim robot stands on your real table, aligned with a one-time two-point
    calibration (touch the table's near-left and near-right corners).
  * Room scan: WebXR `plane-detection` and `mesh-detection` (Quest) send the planes as boxes in a `world set` scene,
    so your room becomes the scene.
  * Live teleop: your hand pose drives the robot's end effector (`{type: "teleop", role, p, q, grip}` at about
    30 Hz), and P1 records it. This gives the best demonstrations.
  * **Tested without a headset** with the Immersive Web Emulator or a mocked `navigator.xr` in a check. A real
    Quest test is listed as manual.
* **As built** (core + desktop authoring, PR for #29; VR / `web/xr.js` is the follow-up; details in `docs/PROTOCOL.md`
  → "v7 · Trajectories in 3D"):
  * `pps/traj.py` is pure (numpy only, `tests/test_traj.py`): `normalize`, frames, `densify`, `check`,
    `from_keypoints`, `select` / `edit` / `insert`, `from_demo`, `describe`, and the runtime glue `follow_step`.
    `pps/features/traj.py` owns the message, `state.traj`, the checks and the plan card. `web/ui/traj.js` is the editor.
  * Schema additions (all optional, absent when unset): per point `yaw` and `tilt` (degrees, relative to the default
    approach orientation; an absolute `q` wins) and `hold` (seconds); `pattern.span` (point range), `pattern.apply`
    (false for a demonstration, whose points already contain the weave); `meta` (free-form: the language keypoints,
    notes, which objects it was lifted over, the 2D profile). `object:<name>` frames have their origin at the object's
    top centre with world-parallel axes (they follow the object's position, not its rotation).
  * Timing deviation: "min-jerk" is the shape of every start and stop (quintic ramps, 0.5 s), with constant speed in
    between, rather than a min-jerk segment per point (which would stop at every point of a drawn stroke). The hand
    also stops for 0.4 s wherever the gripper is commanded.
  * `state.traj` adds `ghost` (what to draw), `info` (per point: height, nearest object), `issues`, `objects`,
    `surface`, `rev`, `reply`, `plan_id`, `progress` and `t` to `{current, proposed, ok, why, running, i}`.
  * Execution goes through the existing path follower: an installed trajectory is `rt.path` with timed samples, so
    `follow_path`, F, "Run path", plan preview and "carry it along my path" all apply. Hooks in P0's files are three
    small, marked lines: `Runtime.precheck(quats=)`, the timed `FOLLOW` branch in `update_targets`, and
    `set_path_world` marking drawn paths (`src: "draw"`). Strokes and 3D-editor paths keep their old checks
    (reach + zones) until edited; then the full check (reach with orientation, surface, objects, zones, P5 hooks)
    applies.
  * Physics: `force` and `grip` are passed to `rt.set_force` / `rt.set_gripper` when P0 provides them; otherwise the
    gripper is a kinematic grasp of the object at the hand and force is only recorded. `teleop` is not registered here
    (VR follow-up).
  * Agent: `make_trajectory`, `edit_trajectory`, `run_trajectory`; the context carries the shown trajectory's points
    so "higher there" / "slower near the vase" resolve to point numbers. P3's demo `replay` now proposes the demo as a
    `source: "demo"` trajectory (person's hand orientation dropped, timing and pinch-grip kept).
  * Desktop UI: the "Path" dock tool is now keyframes (the legacy click-to-add waypoint editor stays in `view3d.js` but
    its toggle is hidden, as before, whenever a module owns the Path tool).
* **As built: VR / MR** (PR for #30; guide `docs/vr.md`, messages `docs/PROTOCOL.md` → "v8 · VR / MR and live teleop"):
  * `web/xr.js` is the WebXR glue (session, rendering through the 3D stage's renderer and scene, input, panels);
    `web/xr-core.js` is pure (XR ↔ sim alignment, gestures with hysteresis, strokes, the input → message pipeline, room
    → scene) and unit-tested under node (`tests/xr_core.test.mjs`). The ghost, handles and labels are the desktop's
    (`web/ui/traj.js` draws into the shared scene); VR only adds `window.PCTraj.preview/track/cancel` so a hand moves a
    handle with the same local preview as a mouse. Hooks in `view3d.js`: `PC3D.renderer` / `geoms` / `sceneReady`, the
    desktop loop pauses while presenting, geoms carry `userData.gm` (MR ghosts static furniture, hides the floor).
  * Alignment: sim = Rz(yaw)·R0·xr + t. VR recentres from the head pose; MR solves it from two touched corners
    (`side` "across" = you face the robot across the table (default), "behind" = its view), saved in `localStorage`
    with a persistent anchor when granted (re-based when the anchor moves).
  * Deviations: pinch *distance* → speed is one of three options ("Speed: robot's / as drawn / pinch"); the default is
    the robot's speed. Grabbing a ghost gripper moves an existing point (keyframes come from quick pinches). The room
    scan can only send what the scene spec describes (the surface template and boxes on it); walls and furniture away
    from the table are previewed, not simulated. `hit-test` is requested but unused.
  * `teleop` (`pps/features/teleop.py`): clutch-relative hand motion from the headset, clamped (reach, surface), rate
    limited and scaled by P5 safety, no motion during a protective stop or into the person; P3 mirroring now goes
    through it. P1 recording shows in VR when `state.dataset` exists.

## P3 Watching the person (`pps/human/`, `pps/features/watch.py`, `web/ui/watch.js`)

This extends the co-presence layer (`pps/features/copresence.py`, which already provides pointing, the open hand and
attention) into a model of what the person is doing.

* **Perception.** The person is represented in the robot's world frame (as co-presence already does):
  * 3D body pose: 33 landmarks.
  * Hands: wrist pose, pinch (thumb–index distance) and open or closed. MediaPipe Hands runs in the browser when a
    camera is on; VR hands are used when available.
  * Held tool: an object or tool near the hand, from YOLO, Gemini ER, or the closest sim object.
  * Speed and fatigue cues.
* **Understanding.**
  * `pps/human/activity.py` segments motion into phases with rules: repetitions, still or moving, the hand path's
    periodicity.
  * A VLM summarizer (Gemini or OpenAI vision via BYOK or `.env`; `--offline` uses the rules only) describes the
    scene every few seconds: "squatting, rep 4, knees caving in".
* **State.**
  ```json
  "human": {"visible": true, "src": "webcam|phone|vr|synthetic", "pose": [[x,y,z]*33],
            "hands": {"right": {"p": [..], "q": [..], "pinch": 0.02, "open": false}},
            "holding": "torch"|null, "activity": "squat", "phase": "down", "reps": 4,
            "speed": 0.4, "summary": "...", "t": 12.3}
  ```
* **Modes.** `{type: "watch", op: "mode", mode: "off|mirror|learn|respond|assist|coach"}` and `state.watch = {mode, rules, events}`.
  * `mirror` copies the person live. It works for every body: humanoids retarget the whole body, and arms follow
    the person's hand pose (wrist position and orientation, pinch drives the gripper).
  * `learn` records a demonstration. When it ends, P4 extracts a skill and the robot repeats it as a proposed
    trajectory.
  * `respond` runs rules: `{type: "watch", op: "rule", when: "hand_open near robot" | "holding torch and visor
    up" | free text, do: "hand over the wrench" | <task>}`. Free-text rules are compiled by the agent into
    predicates over `state.human`, and rules can be added by voice ("when I put my hand out, give me the wrench").
  * `assist` is physical help that follows the person, through P0 impedance control and P5 safety: spot the bar,
    steady the workpiece, hold the other end.
  * `coach` compares the person to a reference motion (a skill or video) and speaks short corrections and counts
    reps.
* **Agent.**
  * `observe` returns `human`.
  * New tools: `set_watch_mode`, `add_watch_rule`, `learn_from_demo`, `mirror_person`.
  * The base prompt teaches the agent that "do it like me" or "watch me" means watching, not text parsing.
* **As built** (PR for #31; details in `docs/PROTOCOL.md` → "v6 · Watching the person"):
  * `pps/human/`: `model.py` (the person in the world frame), `activity.py` (rule-based activity, phase, reps,
    stall), `coach.py` (references and cues), `rules.py` (predicates and the offline phrase compiler), `demo.py`
    (recording, file format, stub extractor), `vlm.py` (summarizer), `synth.py` (synthetic people for checks).
  * `state.human` has the keys above plus `pose_filled` (indices of the 33 that are estimated: the server pose model
    gives 19 points, face and feet are filled from the head and ankles), `holding_hand`, `offer`, `stalled`,
    `fatigue`, `weave` (`{amp, freq, travel, axis, dir}` while weaving) and `summary_src` (`rules` | `gemini` |
    `openai`). Hands carry `src` (`hands` = browser MediaPipe Hands, `pose` = pose points only) and `near_robot`.
    The body is grounded (lowest ankle on the floor), so hips really drop in a squat (co-presence keeps them fixed).
  * `state.watch = {mode, rules, events, mirror, learn: {recording, seconds, frames, last}, assist, coach, hand,
    fires, reply, summary, demos}`. Every `watch` op answers in `watch.reply = {id, op, ok, message, ...}`.
  * Extra ops: `rule` also takes `text` ("when I …, …") or `expr` (a compiled predicate) and `task` (a task message);
    `rule_remove`, `rules_clear`, `learn_start`, `learn_stop`, `replay`, `tool` (declare what you hold), `coach_ref`,
    `summary` (opt-in VLM), `reset_reps`. Browser hand keypoints arrive as `{type: "hands", hands: [{uv, lm, score}]}`.
  * Deviations: rules are evaluated in `respond`, `assist` and `coach` (not while mirroring or learning); the
    synthetic no-camera dancer never fires rules or coaching. The VLM summarizer is opt-in (`summary` op, UI "AI"
    chip) because it sends camera frames to a provider; it is off in BYOK mode (no server key). Physical assist force
    is only *requested* (`watch.assist.request = {force_n, dir}`) for P0 impedance control to apply. Mirroring on
    arms drives the hand target directly (or the P2 `teleop` message when that handler exists) and grasps
    kinematically next to an object unless the runtime has `set_gripper` (P0).
  * Agent: `observe` returns `human` (without the 33-point pose) and `watch`; tools `set_watch_mode`,
    `add_watch_rule` (built-in terms or a compiled `expr`), `remove_watch_rule`, `learn_from_demo` (start | stop |
    replay), `mirror_person`.

## P4 Skills from demonstration (`pps/skills/`)

* **Parametric skills.** A demonstration (P3 `learn`, a video, or a VR teleop take) becomes a skill with
  parameters, expressed relative to objects. Raw replay is not the goal:
  * `weave_seam {seam: object|polyline, travel_speed, work_angle, travel_angle, standoff, weave: {kind, amp, freq}}`
  * `wipe {region, force, pattern, passes}`
  * `stir {container, radius, freq, depth}`
  * `press {target, force, hold_s}`
  * `spot {object (bar), follow: "hands", assist_when: "bar velocity < v_min for t", max_force}`
  * `mirror_motion {clip}`: humanoid whole-body motion (the existing video → skill path)
* **Extraction.** Fit from the hand path and held tool:
  * the dominant direction and speed;
  * a periodic component (FFT on the lateral offset gives the weave amplitude and frequency);
  * orientation statistics.

  The agent names the skill and confirms the parameters with the person ("4 mm zigzag at 2 Hz, 5 mm/s, 15° push.
  Right?"). Geometry gives precision: the seam position snaps to the workpiece edge, and the person gives the
  style.
* Skills compile to P2 trajectories, are saved in `skills/` (JSON) and are listed on the existing timeline.

## P5 Safety around people (`pps/safety.py`)

* **Speed and separation monitoring** (in the spirit of ISO/TS 15066):
  * the distance from the robot's links to the person's body (P3 pose, as capsules) sets a speed scale;
  * a protective stop below `d_stop`;
  * the robot slows inside `d_slow`.
* **Contact.**
  * In `assist`, end-effector force is capped (P0 impedance), and contact is allowed only on the hands and
    forearms.
  * Head and torso contact means an immediate stop.
* **State.** `state.safety = {d_min, speed_scale, stop, reason, zone}`. The 3D view draws the person's safety
  capsules, and the plan card shows "slowing: you're 30 cm away".
* Safety cannot be turned off from the UI, and a check proves the stop.

## P6 Real-to-sim calibration (`pps/calib/`, `scripts/calibrate.py`)

* **Domain randomization** of P0 parameters for P1 generation: friction, mass, damping, gains, latency, lighting and
  textures.
* **System identification.** Given a recorded trajectory (joint positions and object poses over time), fit
  `{friction_scale, mass_scale, damping_scale, kp_scale, latency_ms}` so the sim rollout matches. This uses CMA-ES,
  or scipy `differential_evolution` when `cma` is missing.
  * **Proof without hardware:** a "hidden real" robot is the sim with secret parameters. Calibration recovers them
    within a stated tolerance from one or two probe motions (push, lift, swing).
* **Probe routine.** `{type: "calib", op: "probe"}` makes the robot run the probes in the current world and reports
  the fit (`state.calib`). In the real world this runs once per home: a new floor or table means a new friction
  estimate.
* **Real robot bridge (interface only).** `pps/bridge/` defines the `RobotDriver` protocol: `read_state`,
  `send_q_des`, `send_gripper` and `stop`. It includes a sim driver and a stub for LeRobot / ROS 2, so the same plans
  can drive hardware later. No hardware is claimed.

## Demo packs (`pps/world/packs/`)

* **Weld cell.**
  * A table with two steel plates forming a seam, and a torch tool on the arm (UR5e or Panda) with its tip TCP.
  * The person demonstrates the weave with a hand, phone or VR controller. The robot welds the seam with the
    extracted parameters, and the bead is drawn as a growing tube with the weave pattern.
  * No arc or melt physics (stated).
* **Gym.**
  * A bench and a barbell (a free body, 20 kg); G1 or Apollo coaches and spots.
  * `coach` counts squats and corrects form against a reference.
  * `spot` follows the bar and helps (force-limited) when it stalls.
  * The person is the webcam pose (or synthetic), not a physical body in contact.
* **Workshop helper.** Tools on a table. "When I put my hand out, give me the wrench" works as a `respond` rule.

## Rules for every workstream

* **Branching and PRs.** Branch from `v1/integration`, open a PR into `v1/integration`, and link the issue.
* **Self test.** `.venv/bin/python scripts/selftest.py` must stay green. Add a check in `scripts/checks/` for every
  feature.
* **Ports.** Each workstream gets its own range (below) and never touches 8777, 8443 or 8780.
* **Secrets.** Never print, log or commit `.env` or API keys. Tests use `--mock`/offline paths. Live LLM calls happen
  only in manual checks.
* **Resources.** The machine is short on RAM and disk:
  * run one server at a time;
  * close headless Chrome when done;
  * no large downloads (> 300 MB) without asking;
  * clean temp files.
