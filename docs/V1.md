# PhysicsClay v1: physical, watchful, open (contract between the v1 workstreams)

The hackathon build (UX 2.0 and UX 3) proved the interaction model: say, point and show, and the robot proposes
while you correct. It also cut three corners that an open-source robotics project cannot keep:

1. **No physics.** The robot is posed by IK (`mj_forward` only, no `mj_step`). A picked object is teleported to the hand
   (mocap), so nothing slips, falls, collides or weighs anything. The recorded data cannot teach a real robot.
2. **The person is only a pointer.** The robot sees where you point and whether your hand is open. It does not
   understand what you are *doing* (welding, squatting, reaching for a tool), so it cannot work with you, coach you,
   or learn a technique by watching.
3. **Trajectories are 2D.** A drawn path is a stroke projected onto the table plus a fixed hover height. There is no
   height, wrist orientation, speed, force or tolerance, and no good way to author those in 3D.

v1 fixes all three, makes everything a dataset, and packages it as an open-source project people can install,
extend and trust. The principles stay the same. Language is coarse and the robot proposes. You fix only what is
wrong, by showing, pointing, drawing (in VR if you have it) or talking.

---

## P0 Physics (`pps/physics.py`, `pps/world/*`, `pps/robot_runtime.py`, `pps/tasks.py`)

**Physics is the default. `PC_PHYSICS=0` (or `--kinematic`) keeps the old kinematic mode as a fallback.**

* **Control loop.** IK stays the *planner*. It solves on its own `mink.Configuration` (a copy of the model) and produces
  the desired joint positions `q_des`. The *plant* is `mujoco.MjData` stepped with `mj_step` at the model timestep
  (2 ms) for `n_sub = round(dt / timestep)` substeps per server tick. The plant tracks `q_des` with:
  * position actuators (`<position kp=… kv=…>`, or the model's own actuators when it has them), or
  * joint-space PD as `qfrc_applied` when a model has no usable actuators (`ctrl_mode: "pd"`).

  Gains and effort limits come from the profile, with sensible defaults per kind.
* **Objects** are free bodies (`<freejoint/>`) with mass, inertia and friction (`condim=4`, torsional friction) instead
  of mocap. Names stay `obj_<name>` (movable) and `obs_<name>` (fixed, no joint). Tasks read poses from `data.xpos` /
  `data.xquat` of the body. Every place that used `mocap_pos[obj]` goes through one helper.
* **Grasping is by contact.**
  * Grippers have real finger joints and actuators: Panda fingers, Robotiq 2F-85 on UR5e (from MuJoCo Menagerie if it
    is present, otherwise a simple parallel-jaw gripper built in XML), xArm gripper, ALOHA fingers.
  * Humanoid hands without fingers get a simple two-pad parallel gripper on the palm site.
  * A grasp succeeds only when both pads touch the object and it lifts with the hand. Slip is detected: the object
    lags the hand or falls, and the task fails honestly ("it slipped").
* **Humanoids.**
  * Manipulation runs with the pelvis welded (`base: "legged"` and `physics_base: "fixed"`). The legs are
    PD-held at the stand keyframe.
  * Dynamic walking is out of scope (it needs a learned locomotion policy). This is stated in the profile note and
    the docs.
* **Compliance.** `impedance` mode: lower stiffness, an effort cap and a force limit at the end effector, used for
  wiping, pressing and anything that touches a person. A per-task `force` (N) is tracked along the approach axis by a
  simple admittance outer loop on `q_des`.
* **State.** Physics keeps the existing `state.world` / `state.task` keys. It adds:
  ```json
  "physics": {"mode": "dynamic"|"kinematic", "dt": 0.002, "rtf": 1.0,
              "grasp": {"right": "red_cup"|null, ...}, "ee_force": {"right": [fx, fy, fz]},
              "contacts": [{"a": "right_pad", "b": "obj_red_cup", "f": 3.2}], "params": {...}}
  ```
* **Message.** `{type: "physics", op: "set", params: {friction_scale, mass_scale, damping_scale, kp_scale, latency_ms,
  gravity}}` changes the plant parameters at run time (used by P6 randomization and calibration). `op: "reset"`
  restores the defaults.
* **Done when** the full self test passes in dynamic mode, and every robot except experimental ones does a real
  contact pick & place. A new physics check proves:
  * an object dropped from 10 cm lands and rests;
  * a pick with gripper force 0 fails as a slip;
  * a heavy object (`mass_scale` 20) is refused or dropped honestly;
  * impedance mode keeps the end-effector force under its limit while pressing on the table.

### P0 as built (notes for the other workstreams)

* **Where things are.** `pps/physics.py` (the plant: control, sensing, parameters, grippers, spec changes),
  `pps/world/scene.py` (`build(..., physics=None)` compiles the planner model `world.ik_model` and the plant
  `world.model`), `pps/robot_runtime.py` / `pps/world/runtime.py` (`rt.plant`, `rt.q_des`, `rt.ik_data` = the plan,
  `rt.data` = the plant), `pps/tasks.py` (grasp planning, slip / weight / placement checks, `press`).
* **Reading the robot.** `rt.data` is the plant everywhere (rendering, `/scene.json`, `geom_poses`, tasks, features).
  Robot joints are the first `rt.nq_r` entries of `rt.data.qpos`; `rt.q_des` is the action (P1). Objects: always
  `tasks.obj_pos(name)` / `obj_mat` / `mug_center` / `set_obj_pose` (mocap in kinematic mode, a free joint with physics).
  `state.physics.objects` has every movable object's pose and speed.
* **Deviations from the contract above (and why).**
  * Joints without an actuator (G1, H2, Stretch's base slide) get **position servos added in the plant** instead of a
    `qfrc_applied` PD: an explicit PD on light links is unstable at 2 ms, the implicit actuator damping is not. All
    servos get velocity feed-forward and gravity compensation that counts against the actuator's force limit.
  * Unchanged keys plus extras: `state.physics` also has `substeps`, `time` and `objects`; the `physics` message also
    takes `grip_force`, `impedance`, `force_limit` and `op: "drop"` (a test probe); the task action `press` is new
    (P4's `press` skill can call it).
  * The UR5e and iiwa14 get a built parallel-jaw gripper with a 14 cm stroke (Robotiq 2F-140 class; Menagerie is not on
    disk), humanoids a two-pad gripper on the palm (15 cm). Stretch, TidyBot (Robotiq 2F-85), xArm, Panda, ALOHA and Spot
    use their own fingers with force calibration (`boost` in the profile).
* **What the planner learned** (it now drives a physical robot): an orientation per waypoint (grasps turn the hand,
  transit goes home), a joint velocity limit (the plant's servos can't follow arbitrarily fast IK), the other objects
  and fixtures as obstacles for the hand and wrist, gripper / arm self-collision on the G1, a slow last segment into a
  grasp / release / press, and a lift over the table edge when the hands start below it. A pick tries a few ways in
  (jaw yaw for top grasps; approach heading and pitch for side grasps; the other hand on two-armed bodies) and runs the
  first one the IK can trace.
* **Humanoids** (G1, Apollo, H2) and Spot: the base is welded to a harness that follows the planned base pose; the legs
  track the IK with their servos and the feet stand on the floor. No dynamic balance or walking (needs a learned
  policy); the profile note says so in `state.world.robot.note`. Apollo's dexterous hand is rigid in the model, so its
  meshes don't collide and the palm's two-pad gripper does the grasping.
* **Mobile bases**: the base joints are actuated (TidyBot's own position servos, a servo added on Stretch's base slide);
  driving moves the planned base and the plant follows. The wheels don't roll (abstracted), robot-floor contacts are off
  for non-legged bodies.
* **Objects**: the scanned mug collides as a hollow mug (bottom, 12 wall segments, handle) so narrow grippers can hold
  it by the rim; other kinds are boxes / cylinders. Masses per kind scale with size; friction `condim=4`.
* **Grip, slip, weight**: the close / open commands ramp over 0.8 s (no slamming); a grasp is an attempt until the slip
  monitor confirms it (object drifts > 5 cm from where the jaws hold it, or one jaw loses contact > 0.3 s → "It slipped");
  the wrist feels the weight once the object hangs free (> payload → "Too heavy", let it back down).
* **Real contact pick & place per robot** (v1 P0b; `scripts/bench_grasp.py -n 10`: the default table scene, mug → center
  and red block → center, each object nudged ±1.5 cm and ±15° per trial, success = the task says done, the object rests

  body below 9/10 on either is listed as `experimental` in physics mode with the reason in its note (the WORLD.md rule);

* **What made grasps reliable (P0b).**
  * Contact: `impratio = 1` (at 2 ms the default-plus-elliptic setting made light objects wobble and turn in the jaws)
    and stiff pad contacts (`solref 0.004`, `solmix 100` so the pad's parameters win, `condim 4`). Pads are added from
    the finger meshes where a model's collision geoms sit inside the fingers (ALOHA), so the grip is at the real tips.
  * Control: the servo setpoint is velocity- and acceleration-limited (`A_MAX` 10 rad/s², time constant 30 ms) with the
    plan's velocity fed forward (not for an impedance-mode arm: with its small kp the feed-forward became a 20 Hz force
    ripple against the surface), so an IK jump can't kick the held object; joint damping is fed forward; hinge armature
    is at least 0.02 (iiwa's wrist spun objects without it); tendon-driven joints (Stretch's telescoping arm) track by
    a tendon servo.
  * Grasp: hover → settle (the hand stops over the object until the arm lined up, ≤ 1.5 s) → re-aim at where the
    object really is → close → lift; the jaws must reach the grasp within 1.5 cm (`CRIT_TOL`) or it says so. Spot's
    fixed jaw is planned as the fixed side; side grasps (Stretch) use the gripper's own "up".
  * Place: over the spot the hand stops until it lined up, the way down is re-aimed with the object's real offset in
    the hand, it lets go once the surface carries the object (support force > half its weight, or still for 0.1 s), and
    the done message reports the measured error ("…, 0.8 cm from the spot"). Free spots count the hand's footprint
    and are tested with the planner the way the place really goes; top grasps try hand headings that clear the other
    objects (`_place_yaw`).
  * Clearance: the whole arm keeps off the table (not only the hand), the carry height clears the movable objects, the
    hand geoms are obstacles for the other objects; legged bodies avoid their own legs/torso (Apollo) and two arms keep
    apart. Profiles may set `physics.home`, `exclude`, `stiffer` and a `mount.z` riser.
  * The planner starts every plan from the measured arm (joints clipped into their ranges) rather than from the last
    plan, and a path waits while the hand trails the plan by > 3 cm (≤ 2 s).
  * Refusals don't stall the loop. A pick sent by the server (and each goal move) is a resumable search: the free-spot
    reach tests and the ways in (up to 8 per hand) run a slice per frame (`state.task.status == "planning"`, about one
    plan per frame, `Tasks.search_tick`), and a new command drops it. A hand whose arm stretched out (the sum of its link
    lengths from the shoulder, + 10 cm, + 15 cm for legged bodies; mobile bases have no bound) can't reach the object or
    the spot is out before any IK; if no hand can, the main way is planned once, for the message, the red waypoints and
    the nearest reachable spot. (Since the final behaviour pass the search is a planning job that pauses between IK
    waypoints, and the plan card's dry run and a goal's set-aside spots are jobs too: "No planning stalls" below.
    Scripts and the benchmark still plan in one go, `sliced=False`.) The server
    caps the planner's step at the plant's substep cap so plan and plant share one clock under load
    (`dt = min(dt, plant.sub_cap * DT)`).
* **Two-arm handover** (`{type:"task", action:"handover", object, to, target}` on ALOHA; `tasks.handover_arms`): one arm
  picks the object by its near end, the hands meet in the middle 14 cm above the table, the other hand closes on the
  free end (re-aimed at where it really is), the hold is checked by contact, the first hand opens and backs off, then
  the receiver places it. Long objects only (≥ ~20 cm). `scripts/checks/handover.py` checks the transfer (right jaws →
  left jaws, never unheld in the air) and the refusal on one-armed bodies.
* **Checks adjusted (P0b), and why.** `checks/candidates.py` sets the green block at (0.30, −0.42) in physics: at its
  UX 2.0 spot only the kinematic super-reach got it. `checks/gestures.py` nudges away from the vase in physics: the G1's
  18 cm side gripper doesn't fit 2 cm closer to it. `checks/zones.py` starts the mug east of zone A in physics for the
  pick & place detour: the spot beside the vase the kinematic (point) hand used doesn't fit the G1's gripper, and the
  nearest one that does is right next to the mug, so the carry wouldn't pass the zone. `checks/goal.py` starts the red
  block at (0.30, −0.42) in physics for the swap: at its UX 2.0 spot right behind the mug, the set-aside spots the swap
  needs are past what the G1's side grasp physically reaches (kinematic super-reach again). `checks/gestures.py` resets
  the scene before the nudge: with physics the drawn "go on" path before it runs the hand through the mug and knocks it
  over (the path check only tests reach; see limitations). The self test waits by sim time in physics, waits up to 30 s
  for a state frame (a plan is made inside one server tick) and `PC_SELFTEST_CHECKS=a,b` runs only those check files.
  `op:"place"` is a test probe (`{type:"physics", op:"place", object, pos:[x, y]}`).
* **Limitations (P0b).** The G1's side grasp keeps the heading it took the object with, so it places reliably only in a
  band about 27–36 cm out at table height (further out to its side); spots past that are refused honestly. (The
  P0b limits on drawn paths vs objects, arm clearance, Stretch 3, Spot and TidyBot are resolved in P0c below; one slice
  being a whole plan, and the dry run and a goal's set-aside choice planning in one go, in "No planning stalls".)
* **Every body grasps for real (P0c).** Stretch 3, TidyBot and Spot leave the experimental list (table above; only H2,
  whose hands aren't driven, stays). Still contact only: nothing is welded or attached to a hand.
  * *Stretch 3's SG3* (`profiles._sg3_grip`, `physics._parallel_pads`): the model's rigid hinged fingers closed the tips
    along an arc, tilted up to 30°, and squeezed objects out. The real fingers are flexible strips with suction-cup
    tips that swivel flat, so physics models the tips as two parallel, spring-loaded pads: each pad's carrier follows
    the model's own fingertip face across the jaws for the gripper slide s (a cubic fitted to the finger kinematics,
    coupled by an equality), and the pad sits behind it on a slide with a spring and damper (5 kN/m, ≤ 1.2 cm: the
    finger's flex). The force is the gripper's own force-limited servo through that coupling (`boost` 3.7 ≈ 2 dx/ds).
  * *Spot's claw*: the moving finger is a 9.4 cm wide plate that swings down in an arc onto the fixed jaw (8.2 cm). At
    its old opening it landed on the mug's far rim and wedged the mug in the claw; a rim pinch can't work either (the
    finger is wider than the mug's inside). For an object that nearly fills the claw the finger opens to −1.25 rad
    (`wide_open`), comes down outside the far wall and holds 5 cm below the top (`deep`), and lets go only as wide as
    it opened (`Plant.grip_cmd(role, "open", to=…)`). A rim grasp by a one-jaw gripper keeps the jaw outside the wall.
  * *TidyBot*: its Kinova trails the plan by 3–5 cm in transit and cut the corner into the mug on the way to the block.
    For such a body (`physics.transit_over`) the way in goes over the other movable objects (`_clear_z`: the open
    hand's reach below the TCP and its footprint) instead of skimming past them; for every body the way home after a
    place does (Stretch 3's home is low over the work area, and TidyBot came down on the block it had just set down),
    except past what a side gripper backed away from and only moves away from (the G1's pick got 2 s longer for nothing).
    If those lifted waypoints are what an arm can't reach (Spot), the pick is planned again without them, so the lifts
    never make a plan worse. (An extra waypoint on the way in shifts a 7-DoF arm's posture at the grasp: for every
    body it cost xArm7 block placements just past the 3 cm bar, so it is per body.)
  * *Letting go*: the jaws open 35 % of their travel past where they came free, or stop when the hand touches a
    neighbour (`RELEASE_OPEN`, `Plant.hand_bump`, gripper command `hold`), instead of all the way (the 17 cm SG3 jammed
    against the vase beside the spot). Side jaws keep `room` beside the object, across the heading, when a free spot is
    chosen; from above, the hand stops high enough over a grasp for long fingertips to clear the top (`_pre_dz`).
  * *Arm clearance*: the planner keeps the rest of each arm (forearm, upper arm, up to the torso / legged body / mobile
    base) clear of the objects too: a second `CollisionAvoidanceLimit` (8 mm, vs 12 mm for the gripper and last links;
    `Runtime._obstacle_links`).
* **Paths respect the objects (P0c).** With physics a drawn stroke / 3D-editor path (`tasks.set_path_world`) is checked
  against the objects it passes: the hand as it is held (the corners of its gripper's collision geoms around the TCP,
  `Tasks.hand_points`, with the two wrist links above the gripper) vs the objects and fixed obstacles as upright
  cylinders (`tasks.path_object_hits`). Over a movable object the path is lifted 5 cm over its top within 3 cm of its
  outline, with 45° ramps, when the arm reaches that high (`tasks.lift_path`; "…, lifted over the mug"). Waypoints go red
  only for a real overlap of that hand with an object (no margin: mesh bounding boxes already overstate a hand); into a fixed one (the vase is never flown over, as with a carry), or when the lift isn't reachable, the
  waypoints go red and `path.why` says what it would hit, worded like the P2 checks ("my gripper would hit the vase");
  follow_path refuses with it. Following a path the planner treats every object but what the hand holds as an
  obstacle, and the lead-in to the start is lifted the same way. P2 trajectories get a gripper check through
  `traj.register_checker` (`pps/features/clearance.py`): samples where the gripper's reach straight below its TCP (the
  open fingertips, a side gripper's pads: `Tasks.grip_reach`, as the pick planner sees it, since a trajectory sets its
  own wrist orientation) would go into an object go red and the issue says where; what a grip closes on, what the hand
  holds and what a key point sits on are not obstacles, and the move to the start stays traj.py's own check. The
  kinematic fallback is unchanged (the hand is a point there).
* **Checks and tests (P0c).** `scripts/checks/grasp_bench.py` runs a fast bench subset in the self test (Stretch 3,
  Spot, TidyBot and the Panda, 2 trials per task, in its own process: sim time, so the verdicts don't depend on the
  machine's load; `bench_grasp.py --json`); `scripts/checks/paths.py` checks the lift over the mug (and that following
  it leaves the mug standing), the red path into the vase and its refusal, the kinematic fallback, and a P2 trajectory
  whose gripper skims the mug; `tests/test_path_objects.py` unit-tests the path geometry.
* **Limitations (P0c).** The planner is still reactive IK, not a motion planner: rarely a hand wedges between two
  objects with joints at their limits on the way down to a spot and says "my arm couldn't follow that path", or refuses a
  spot it could reach another way (iiwa14's block, seed 1: 9/10 before and after P0c). The hand-vs-object path check models objects as upright cylinders and the
  hand as its geoms' corners at its current orientation; a stroke adopted by P2 is run by its timed follower (its own
  straight approach to the start and wrist orientation), along which the G1's wrist link (its rubber hand) can still
  brush the mug it was lifted over (1–2 cm in the self test; an arm follows it cleanly). The P2 gripper check looks straight below the TCP only: a
  trajectory whose gripper footprint clips an object's side is caught by traj.py's hand-point check only where the TCP
  itself comes close, and `traj.from_keypoints` lifts over obstacles by a fixed 5 cm, which a hanging gripper (the
  G1's) doesn't fully clear; making those keypoint lifts and the approach to the start gripper-aware (with
  `Tasks.hand_points`) is the follow-up in pps/traj.py.
  The bench is deterministic for a given code and seed, but contact is chaotic: one trial's history shifts the next,
  so single-trial differences between versions are noise (compare over seeds).

  The server caps substeps when a body can't keep up and reports it as `rtf < 1` (H2).
* **No planning stalls (final behaviour pass, `pps/slicing.py`).** One IK trace of a path costs 0.1–0.6 s on a busy
  machine (1.5 s at worst) and a refusal tries a dozen, so a plan made inside one server frame froze the stream: a plan
  card's dry run of a refused pick 21.8 s, of an ordinary pick 2.1 s, a goal swap's set-aside spots 2.4 s (G1, physics,
  load ~90 on 10 cores, longest gap between two state frames at a client).
  * A `Job` runs a planning call on a helper thread that only runs while the server thread waits for it (they hand
    control to each other: a stackful coroutine, so the planner stays plain synchronous code). It pauses at
    `slicing.point()`: every two IK steps of `Runtime.precheck` (`_trace`, which sets the waypoint target again after a
    pause) and after each way in (`tasks._drain`), once its share of the frame is used up. Between slices the loop keeps
    its own task, path, hand targets, orientation weights, IK obstacles and gripper commands (`Tasks._swap`), so a
    half-made plan never moves the robot; when the job ends its state stands (a task that starts or is refused) or is
    dropped (a dry run, a goal's plan). A new command cancels it: `Cancelled` at its next point unwinds its stack in its
    own state. Outside a job `point()` does nothing (scripts, the benchmark: same plans, same results).
  * Jobs: `pick_place` (`sliced=True`: a registered `(tid, generator)` runs as a job; kinematic picks too),
    `pick_from` / `place_in` sent to the server (`Tasks.run_sliced`), plan cards (`features/plan.py` previews,
    `features/fixtures.py` sequence / fixture cards: the task is "planning" until the card is made), a goal's plan
    (`goal.status == "planning"`). Reach, press, follow_path and the handover steps are single plans and still plan in
    one go.
  * Budget: the loop measures its frames (`state.perf`, `{type:"perf", op:"reset"}`) and gives planning what is left of
    a 0.40 s frame after the rest of it (rendering, physics, state: the recent worst, decaying) and after how far a
    slice may run past its budget (`slicing.stretch()`: the longest recent stretch between two pause points), 10–250
    ms, shared by every job. `perf.plan_stalls` counts frames that planning pushed past 0.5 s (a frame of 0.5 s or more
    that would have been shorter without its planning slice); `perf.plan_frame_max_ms` is the longest frame it ran in.
  * `pps/app.py` runs numpy with one BLAS / OpenMP thread: the IK's small matrices gain nothing from threads, and on the
    loaded machine they thrashed (an IK solve of 8 ms took 120 ms).
  * Results (G1, physics, the same machine): at load ~90 the dry runs and the goal plan took 0.9 s / 19 s / 3.1 s
    across frames with the longest frame 326 / 361 / 333 ms (idle frames up to 137 ms); at a client the longest gap
    between state frames was 388 ms / 904 ms (once; 95 % under 478 ms) / 362 ms instead of 2.1 s / 21.8 s / 2.4 s. The
    plans are the same; the benchmark is unchanged (Panda and G1, 5 trials: 5/5 on both tasks). At load 110+ with 21
    GB of swap, frames pass 0.5 s with no planning at all (idle frames up to 470 ms), and a stretch of two IK steps
    between pause points took up to 390 ms of wall time for 3 ms of CPU (the thread waits for a CPU or a page), so
    the 10 ms minimum budget can still run long: `scripts/checks/stalls.py` then fails and says so (it checks that no
    frame went past 0.5 s because of planning and that planning never took 0.5 s of a frame by itself, with the longest
    frame overall and the idle baseline in the detail). `tests/test_slicing.py` tests the hand-off, the swap,
    cancelling and the shared frame budget.
* **Compliance**: `press` runs an admittance loop on the hand target along the approach axis on the unfiltered contact
  force (guarded approach ≤ 1 cm/s, 4 mm/s for the last centimetre, and the target waits while a compliant hand trails
  it by more than 5 mm: a trailing spring landed at 16–22 N against a 15 N limit); in impedance mode it backs off at
  90 % of `force_limit` and never asks for more than 80 % of it.
* **Merged with the other workstreams** (`v1/integration`):
  * **P5 safety**: `rt.safety_scale` slows the planner (`update_targets(dt·s)`, IK velocity × s, driving × s); the plant
    keeps running in real time and follows the slower plan. A protective stop (s = 0) takes the measured joints as
    `q_des` once and keeps stepping the plant, which holds that pose under gravity and contact; the gripper keeps its
    command and its fingers stop moving (`plant.hold_fingers`). The task layer's grasp / release / press phases pause
    with their clocks (near a person they run at s); the slip monitor still reports an object that really falls.
  * **Adapters**: `rt.ee_force()` → `{role: [fx, fy, fz]}` (P5 cooperative contact, P1 `observation.ee_force`);
    `rt.gripper_state()` (measured from the jaws, 0 open … 1 closed) and `rt.gripper_cmd` (P1); `rt.q_des` is the
    planner's q, the plant's robot qpos prefix (the P1 adapter takes that length and leaves out the built jaws' `pc_`
    joints). All return `None` in kinematic mode.
  * `rt.set_gripper(palm, 0..1)` and `rt.set_force(palm, N)` exist only with physics (in kinematic mode the attribute is
    absent, so P2 trajectory grip events, P3 mirroring and VR teleop fall back to the kinematic grasp). After a manual
    close the task layer holds what both jaws touch; opening, or losing it, lets go. `set_force` is the press task's
    admittance loop as an offset (within 3 cm of the path) on the followed path (P2 point `force`, P4 wipe).
  * **One clock**: when the plant caps its substeps (a busy machine), the server caps the planner's step the same way,
    so the plan never runs ahead of the robot (the whole simulation slows, `rtf < 1`); before, a starved plant lagged
    the plan and grasps closed early or slipped.
  * Between tasks the planner keeps clear of fixtures only (objects are obstacles while a pick / press plans around their
    fresh poses), so a path, mirroring or teleop can close the gripper on any object.
  * **P2 trajectories**: a point that closes the gripper on an object becomes P0's planned grasp of it (TCP position and
    hand orientation from `Tasks.grasp_plan`; the way in from above lines up over it); points without an orientation of
    their own take the grasp's, the hand holds it firmly while the path runs (checked the same way), comes in at 5 cm/s
    and waits 1.2 s at grip points for the jaws. The number of points is unchanged (handles keep their indices).
  * **Teleop (VR)**: the G1's reach sphere counts the gripper TCP past the palm (`rt.tcp_reach`); the operator's wrist
    orientation is tracked firmly while teleop is on (`rt.orient`), because a real gripper must be turned to grasp.
  * **P4**: `mount_tool` edits the spec before both models compile, and the torch replaces the gripper (no jaws are built
    on it; the TCP stays the torch tip); a scene object's `mass` sets its plant mass (the gym barbell is a 20 kg free
    body that stays where it is; `skillbook.bar` still reports the lifter's hold, `follows: false`); spotting's own
    `physics set` (no id) doesn't overwrite a running task's line.

## P1 Datasets (`pps/data/`)

* **Format.** **LeRobot v2** dataset layout under `datasets/<name>/`:
  * `meta/info.json`, `meta/episodes.jsonl`, `meta/tasks.jsonl`, `meta/stats.json`;
  * `data/chunk-000/episode_XXXXXX.parquet`;
  * `videos/chunk-000/observation.images.<cam>/episode_XXXXXX.mp4`.

  It needs `pyarrow` (add it to the deps) and ffmpeg. Each frame records, at a fixed control rate (default 30 Hz):
  * `observation.state`: joint positions and gripper;
  * `action`: `q_des` and gripper command;
  * `observation.images.{front,wrist}`, rendered offscreen at 256×256;
  * `timestamp`, `frame_index`, `episode_index`, `task_index`;
  * `next.done` and `next.success`;
  * optional `observation.human.pose` (33×3 world landmarks, zeros when no person) and `observation.ee_force`.
* **Episodes.** An episode is one task, from start to done or failed. Language comes from the user's words, or a
  paraphrase by the agent. Failed episodes are kept and labelled.
* **Messages.**
  * `{type: "dataset", op: "start", name, auto: true}` records every task as an episode.
  * `op: "stop"` and `op: "discard_last"` end recording or drop the last episode.
  * `state.dataset = {recording, name, episodes, frames, last: {...}}`.
* **Generate.** `scripts/generate.py --seed <traj.json|task.json> --robots panda,ur5e --scenes table,kitchen --n 100
  --randomize objects,physics,lighting` replays one intent as many randomized episodes headlessly (pipeline A in
  `docs/ROADMAP_DATA.md`).
* **Loader check.** A test loads the parquet and video and checks shapes and stats without importing lerobot.
  When `lerobot` is installed, an optional check loads the dataset with `LeRobotDataset`.
* **As built** (PR for #28; how to use it in `docs/datasets.md`, messages in `docs/PROTOCOL.md` → "v8 · Datasets"):
  * `pps/data/lerobot.py` writes LeRobot **v2.1** (`codebase_version`, `episodes_stats.jsonl` and an aggregated
    `stats.json`; video features carry `info` with `video.codec: h264`, `yuv420p`). One dataset per robot body:
    `datasets/<name>/<robot>/` (state and action sizes are per embodiment); scenes and variations are per-episode
    metadata in `episodes.jsonl` (`success`, `outcome`, `robot`, `scene`, `objects`, `language_source`,
    `randomization`, `variation`, `repeated_frames`, …).
  * Cameras (`pps/data/cameras.py`): `front` is a third-person camera across the surface facing the robot, `wrist` rides
    on the first end effector; both are computed per frame and drawn by overriding the OpenGL camera, so no model or
    profile changes (P0's model rewrite cannot break them). The scene's `robot_view` is an optional third camera.
  * Threads: the worker only snapshots (≈0.06 ms per sample); a dataset thread with its own model copy, MjData and
    OpenGL context renders (10–18 ms per sample for two 256² cameras), streams to ffmpeg and writes files. Samples sit
    on an exact 30 Hz wall-clock grid; a grid point between two server frames repeats the last state (counted).
  * Episodes start when a task reaches `running` with the task layer active and end on `done` / `failed`, a takeover
    (`interrupted`), a world rebuild or 120 s. Tasks refused before moving are counted, not recorded. Stopping
    recording drops an episode in progress. Language: the task message's `utterance` / `text` (the browser attaches
    the user's last line, the agent's tasks use the user's turn), else a sentence from the arguments.
  * Extra ops: `randomize` (lighting / camera jitter of the dataset cameras only) and `meta` (JSON added to the next
    episodes) for `scripts/generate.py`.
  * **Physics adapter** (`pps/data/adapter.py`), so P0 is picked up without changes here:
    * `observation.state` = robot 1-dof joints except the profile's `freeze` list (and a legged body's floating base) +
      one gripper value per end effector. Gripper: `rt.gripper_state()` → `{role: 0..1}` (or a dict `rt.gripper`),
      else the task layer's `holding`.
    * `action` = `rt.q_des` (nq-long array in qpos order, or `{joint: value}`) for the same joints + `rt.gripper_cmd`
      (`{role: 0..1}`, else `holding`). Without `q_des` (kinematic): the IK solution at the next sample.
    * `observation.ee_force` = `rt.ee_force()` (or attribute) or `ctx.store["physics"]["ee_force"]` → `{role: [fx, fy,
      fz]}`, the same reading P5 safety uses; the feature exists only if a reading is there when recording starts.
    * **P0 must provide:** `rt.q_des`; `rt.gripper_state()` / `rt.gripper_cmd` once fingers are real; `rt.ee_force()`
      (or `ctx.store["physics"]`); objects as free bodies are rendered from `qpos` automatically (the snapshot copies
      `qpos`, `mocap_pos`, `mocap_quat`). If P0 adds finger joints whose names are not in the profile's `freeze`
      list, they become state joints: keep `freeze` up to date. The generator sends `{type: "physics", op: "set"}`
      when `state.physics` exists.
  * Deviations: no LLM paraphrases yet (the generator takes a `language` list); `observation.human.pose` is flattened to
    99 floats (`nose:x` …); no depth or segmentation; a trained-policy rollout loop is out of scope (P6 bridge).

## P2 Trajectories (`pps/traj.py`, `pps/features/traj.py`, `web/ui/traj.js`, `web/xr.js`)

* **The trajectory object** (one schema for drawn, VR, language, demonstrated and keyframed trajectories):
  ```json
  {"id": "t1", "role": "right", "frame": "world" | "object:<name>", "source": "draw|vr|language|demo|keyframes|skill",
   "label": "over the vase to the right of the bowl",
   "points": [{"p": [x, y, z], "q": [w, x, y, z] | null, "t": 0.0 | null, "grip": 0..1 | null,
               "speed": 0.1 | null, "force": 5.0 | null, "tol": 0.01 | null, "note": "slow here" | null}],
   "pattern": {"kind": "zigzag|circle|figure8", "amp": 0.004, "freq": 2.0, "axis": "normal"} | null,
   "check": {"ok": [true, ...], "why": "...", "duration": 4.2}}
  ```
  `frame: object:<name>` means the points are relative to that object, so the trajectory follows the object when it
  moves. That is how a demonstrated skill generalizes.
* **Compile.**
  * `pps/traj.py` densifies the trajectory: min-jerk timing from `speed`, slerp for `q` and the pattern
    superimposed.
  * It checks each point (reach, joint limits, collisions, zones, safety) and runs it through the P0 plant.
  * `follow_path` becomes a `traj` with `source: "draw"`, and the old messages keep working.
* **Messages.**
  * `{type: "traj", op: "set" | "propose" | "edit" | "run" | "clear", traj?, index?, point?}`.
  * `state.traj = {current, proposed, ok, why, running, i}`.
  * `propose` shows a ghost (a translucent end effector along the path) and needs confirmation, as in plan preview.
* **Authoring on the desktop** (`web/ui/traj.js`, 3D stage):
  * Language first: the agent tool `make_trajectory(description)` has the LLM write keypoints relative to objects
    with height, orientation, speed and force notes, and `pps/traj.py` turns them into a smooth, checked trajectory.
  * Edit with handles: drag a point on its plane, change height with the scroll wheel or Alt-drag, and rotate the
    wrist with a ring gizmo. Each point has speed and force chips.
  * Keyframes: drop 2–5 ghost grippers and they are connected automatically.
  * Voice edits: "higher there" and "slower near the vase" work through the agent.
* **VR / MR** (`web/xr.js`, WebXR, Meta Quest browser, over https on the LAN):
  * An "Enter VR" button appears when `navigator.xr` supports `immersive-vr` or `immersive-ar`.
  * Hand tracking (`hand-tracking` feature) or controllers. Pinch and drag draws a trajectory 1:1 in the air, and the
    pinch distance can map to speed.
  * Grab a ghost gripper to place a keyframe, then twist the wrist to set its orientation.
  * Passthrough (`immersive-ar`): the sim robot stands on your real table, aligned with a one-time two-point
    calibration (touch the table's near-left and near-right corners).
  * Room scan: WebXR `plane-detection` and `mesh-detection` (Quest) send the planes as boxes in a `world set` scene,
    so your room becomes the scene.
  * Live teleop: your hand pose drives the robot's end effector (`{type: "teleop", role, p, q, grip}` at about
    30 Hz), and P1 records it. This gives the best demonstrations.
  * **Tested without a headset** with the Immersive Web Emulator or a mocked `navigator.xr` in a check. A real
    Quest test is listed as manual.
* **As built** (core + desktop authoring, PR for #29; VR / `web/xr.js` is the follow-up; details in `docs/PROTOCOL.md`
  → "v9 · Trajectories in 3D"):
  * `pps/traj.py` is pure (numpy only, `tests/test_traj.py`): `normalize`, frames, `densify`, `check`,
    `from_keypoints`, `select` / `edit` / `insert`, `from_demo`, `describe`, and the runtime glue `follow_step`.
    `pps/features/traj.py` owns the message, `state.traj`, the checks and the plan card. `web/ui/traj.js` is the editor.
  * Schema additions (all optional, absent when unset): per point `yaw` and `tilt` (degrees, relative to the default
    approach orientation; an absolute `q` wins) and `hold` (seconds); `pattern.span` (point range), `pattern.apply`
    (false for a demonstration, whose points already contain the weave); `meta` (free-form: the language keypoints,
    notes, which objects it was lifted over, the 2D profile). `object:<name>` frames have their origin at the object's
    top centre with world-parallel axes (they follow the object's position, not its rotation).
  * Timing deviation: "min-jerk" is the shape of every start and stop (quintic ramps, 0.5 s), with constant speed in
    between, rather than a min-jerk segment per point (which would stop at every point of a drawn stroke). The hand
    also stops for 0.4 s wherever the gripper is commanded.
  * `state.traj` adds `ghost` (what to draw), `info` (per point: height, nearest object), `issues`, `objects`,
    `surface`, `rev`, `reply`, `plan_id`, `progress` and `t` to `{current, proposed, ok, why, running, i}`.
  * Execution goes through the existing path follower: an installed trajectory is `rt.path` with timed samples, so
    `follow_path`, F, "Run path", plan preview and "carry it along my path" all apply. Hooks in P0's files are three
    small, marked lines: `Runtime.precheck(quats=)`, the timed `FOLLOW` branch in `update_targets`, and
    `set_path_world` marking drawn paths (`src: "draw"`). Strokes and 3D-editor paths keep their old checks
    (reach + zones) until edited; then the full check (reach with orientation, surface, objects, zones, P5 hooks)
    applies.
  * Physics: `force` and `grip` are passed to `rt.set_force` / `rt.set_gripper` when P0 provides them; otherwise the
    gripper is a kinematic grasp of the object at the hand and force is only recorded. `teleop` is not registered here
    (VR follow-up).
  * Agent: `make_trajectory`, `edit_trajectory`, `run_trajectory`; the context carries the shown trajectory's points
    so "higher there" / "slower near the vase" resolve to point numbers. P3's demo `replay` now proposes the demo as a
    `source: "demo"` trajectory (person's hand orientation dropped, timing and pinch-grip kept).
  * Desktop UI: the "Path" dock tool is now keyframes (the legacy click-to-add waypoint editor stays in `view3d.js` but
    its toggle is hidden, as before, whenever a module owns the Path tool).
* **As built: VR / MR** (PR for #30; guide `docs/vr.md`, messages `docs/PROTOCOL.md` → "v10 · VR / MR and live teleop"):
  * `web/xr.js` is the WebXR glue (session, rendering through the 3D stage's renderer and scene, input, panels);
    `web/xr-core.js` is pure (XR ↔ sim alignment, gestures with hysteresis, strokes, the input → message pipeline, room
    → scene) and unit-tested under node (`tests/xr_core.test.mjs`). The ghost, handles and labels are the desktop's
    (`web/ui/traj.js` draws into the shared scene); VR only adds `window.PCTraj.preview/track/cancel` so a hand moves a
    handle with the same local preview as a mouse. Hooks in `view3d.js`: `PC3D.renderer` / `geoms` / `sceneReady`, the
    desktop loop pauses while presenting, geoms carry `userData.gm` (MR ghosts static furniture, hides the floor).
  * Alignment: sim = Rz(yaw)·R0·xr + t. VR recentres from the head pose; MR solves it from two touched corners
    (`side` "across" = you face the robot across the table (default), "behind" = its view), saved in `localStorage`
    with a persistent anchor when granted (re-based when the anchor moves).
  * Deviations: pinch *distance* → speed is one of three options ("Speed: robot's / as drawn / pinch"); the default is
    the robot's speed. Grabbing a ghost gripper moves an existing point (keyframes come from quick pinches). The room
    scan can only send what the scene spec describes (the surface template and boxes on it); walls and furniture away
    from the table are previewed, not simulated. `hit-test` is requested but unused.
  * `teleop` (`pps/features/teleop.py`): clutch-relative hand motion from the headset, clamped (reach, surface), rate
    limited and scaled by P5 safety, no motion during a protective stop or into the person; P3 mirroring now goes
    through it. P1 recording shows in VR when `state.dataset` exists.

## P3 Watching the person (`pps/human/`, `pps/features/watch.py`, `web/ui/watch.js`)

This extends the co-presence layer (`pps/features/copresence.py`, which already provides pointing, the open hand and
attention) into a model of what the person is doing.

* **Perception.** The person is represented in the robot's world frame (as co-presence already does):
  * 3D body pose: 33 landmarks.
  * Hands: wrist pose, pinch (thumb–index distance) and open or closed. MediaPipe Hands runs in the browser when a
    camera is on; VR hands are used when available.
  * Held tool: an object or tool near the hand, from YOLO, Gemini ER, or the closest sim object.
  * Speed and fatigue cues.
* **Understanding.**
  * `pps/human/activity.py` segments motion into phases with rules: repetitions, still or moving, the hand path's
    periodicity.
  * A VLM summarizer (Gemini or OpenAI vision via BYOK or `.env`; `--offline` uses the rules only) describes the
    scene every few seconds: "squatting, rep 4, knees caving in".
* **State.**
  ```json
  "human": {"visible": true, "src": "webcam|phone|vr|synthetic", "pose": [[x,y,z]*33],
            "hands": {"right": {"p": [..], "q": [..], "pinch": 0.02, "open": false}},
            "holding": "torch"|null, "activity": "squat", "phase": "down", "reps": 4,
            "speed": 0.4, "summary": "...", "t": 12.3}
  ```
* **Modes.** `{type: "watch", op: "mode", mode: "off|mirror|learn|respond|assist|coach"}` and `state.watch = {mode, rules, events}`.
  * `mirror` copies the person live. It works for every body: humanoids retarget the whole body, and arms follow
    the person's hand pose (wrist position and orientation, pinch drives the gripper).
  * `learn` records a demonstration. When it ends, P4 extracts a skill and the robot repeats it as a proposed
    trajectory.
  * `respond` runs rules: `{type: "watch", op: "rule", when: "hand_open near robot" | "holding torch and visor
    up" | free text, do: "hand over the wrench" | <task>}`. Free-text rules are compiled by the agent into
    predicates over `state.human`, and rules can be added by voice ("when I put my hand out, give me the wrench").
  * `assist` is physical help that follows the person, through P0 impedance control and P5 safety: spot the bar,
    steady the workpiece, hold the other end.
  * `coach` compares the person to a reference motion (a skill or video) and speaks short corrections and counts
    reps.
* **Agent.**
  * `observe` returns `human`.
  * New tools: `set_watch_mode`, `add_watch_rule`, `learn_from_demo`, `mirror_person`.
  * The base prompt teaches the agent that "do it like me" or "watch me" means watching, not text parsing.
* **As built** (PR for #31; details in `docs/PROTOCOL.md` → "v6 · Watching the person"):
  * `pps/human/`: `model.py` (the person in the world frame), `activity.py` (rule-based activity, phase, reps,
    stall), `coach.py` (references and cues), `rules.py` (predicates and the offline phrase compiler), `demo.py`
    (recording, file format, stub extractor), `vlm.py` (summarizer), `synth.py` (synthetic people for checks).
  * `state.human` has the keys above plus `pose_filled` (indices of the 33 that are estimated: the server pose model
    gives 19 points, face and feet are filled from the head and ankles), `holding_hand`, `offer`, `stalled`,
    `fatigue`, `weave` (`{amp, freq, travel, axis, dir}` while weaving) and `summary_src` (`rules` | `gemini` |
    `openai`). Hands carry `src` (`hands` = browser MediaPipe Hands, `pose` = pose points only) and `near_robot`.
    The body is grounded (lowest ankle on the floor), so hips really drop in a squat (co-presence keeps them fixed).
  * `state.watch = {mode, rules, events, mirror, learn: {recording, seconds, frames, last}, assist, coach, hand,
    fires, reply, summary, demos}`. Every `watch` op answers in `watch.reply = {id, op, ok, message, ...}`.
  * Extra ops: `rule` also takes `text` ("when I …, …") or `expr` (a compiled predicate) and `task` (a task message);
    `rule_remove`, `rules_clear`, `learn_start`, `learn_stop`, `replay`, `tool` (declare what you hold), `coach_ref`,
    `summary` (opt-in VLM), `reset_reps`. Browser hand keypoints arrive as `{type: "hands", hands: [{uv, lm, score}]}`.
  * Deviations: rules are evaluated in `respond`, `assist` and `coach` (not while mirroring or learning); the
    synthetic no-camera dancer never fires rules or coaching. The VLM summarizer is opt-in (`summary` op, UI "AI"
    chip) because it sends camera frames to a provider; it is off in BYOK mode (no server key). Physical assist force
    is only *requested* (`watch.assist.request = {force_n, dir}`) for P0 impedance control to apply. Mirroring on
    arms drives the hand target directly (or the P2 `teleop` message when that handler exists) and grasps
    kinematically next to an object unless the runtime has `set_gripper` (P0).
  * Agent: `observe` returns `human` (without the 33-point pose) and `watch`; tools `set_watch_mode`,
    `add_watch_rule` (built-in terms or a compiled `expr`), `remove_watch_rule`, `learn_from_demo` (start | stop |
    replay), `mirror_person`.

## P4 Skills from demonstration (`pps/skills/`)

* **Parametric skills.** A demonstration (P3 `learn`, a video, or a VR teleop take) becomes a skill with
  parameters, expressed relative to objects. Raw replay is not the goal:
  * `weave_seam {seam: object|polyline, travel_speed, work_angle, travel_angle, standoff, weave: {kind, amp, freq}}`
  * `wipe {region, force, pattern, passes}`
  * `stir {container, radius, freq, depth}`
  * `press {target, force, hold_s}`
  * `spot {object (bar), follow: "hands", assist_when: "bar velocity < v_min for t", max_force}`
  * `mirror_motion {clip}`: humanoid whole-body motion (the existing video → skill path)
* **Extraction.** Fit from the hand path and held tool:
  * the dominant direction and speed;
  * a periodic component (FFT on the lateral offset gives the weave amplitude and frequency);
  * orientation statistics.

  The agent names the skill and confirms the parameters with the person ("4 mm zigzag at 2 Hz, 5 mm/s, 15° push.
  Right?"). Geometry gives precision: the seam position snaps to the workpiece edge, and the person gives the
  style.
* Skills compile to P2 trajectories, are saved in `skills/` (JSON) and are listed on the existing timeline.
* **As built** (PR for #32 / #35; details in `docs/skills.md`, `docs/packs.md`, `docs/PROTOCOL.md` → "v11"):
  * `pps/skills/` is pure (numpy): `core.py` (kinds, bounds, files, `describe`, `edit`), `extract.py` (`rank`,
    `extract` per kind, torch angles), `compile.py` (skill + scene → P2 trajectory or behaviour message), `geom.py`
    (seams, footprints, containers), `phrases.py` (spoken corrections). `pps/human/periodic.py` is the shared weave
    math (travel line, FFT, band-limited cycle width, periodicity, the weave gates) used by the live activity reader too.
  * `pps/features/skills.py`: `{type:"skill"}`, `state.skillbook`, auto-extraction when `learn` stops, the "which kind?"
    question through the candidates card, the weld bead (from the TCP's actual path), pack setup (rules, a sentence),
    the gym barbell following the lifter's hands (kinematic only), the synthetic pack demos.
  * Deviations: `spot` and `mirror_motion` are behaviours, not trajectories (watch `assist` with spot parameters;
    `play_skill`). `wipe` also has `spacing`/`speed`, `stir` has `turns`/`direction`, `spot` has `lift_cm`; `weave_seam`
    has `direction`. The torch angle comes from the palm only when the hand clearly points a torch down; otherwise
    defaults are used and said. Small hooks in other workstreams' files: P2 point `roll` and `meta.work_on` (object check),
    P3 `watch` assist spot parameters, `quiet` and demo `smoothing` / no synthetic frames, the candidates question taking
    non-object options, the activity reader's weave gates (the real-camera false positive) and shoulder-height wave.
  * Physics: developed on the kinematic base; force, press and impedance go through P0's messages and task (`press`,
    `physics set impedance/force_limit`) when `tasks.plant` exists, and are only recorded otherwise. Verified at
    integration.

  straight + L seams), gym (G1 or Apollo, bench, 20 kg barbell, gym floor template), workshop (G1 or any picker; wrench,

## P5 Safety around people (`pps/safety.py`)

* **Speed and separation monitoring** (in the spirit of ISO/TS 15066):
  * the distance from the robot's links to the person's body (P3 pose, as capsules) sets a speed scale;
  * a protective stop below `d_stop`;
  * the robot slows inside `d_slow`.
* **Contact.**
  * In `assist`, end-effector force is capped (P0 impedance), and contact is allowed only on the hands and
    forearms.
  * Head and torso contact means an immediate stop.
* **State.** `state.safety = {d_min, speed_scale, stop, reason, zone}`. The 3D view draws the person's safety
  capsules, and the plan card shows "slowing: you're 30 cm away".
* Safety cannot be turned off from the UI, and a check proves the stop.

## P6 Real-to-sim calibration (`pps/calib/`, `scripts/calibrate.py`)

* **Domain randomization** of P0 parameters for P1 generation: friction, mass, damping, gains, latency, lighting and
  textures.
* **System identification.** Given a recorded trajectory (joint positions and object poses over time), fit
  `{friction_scale, mass_scale, damping_scale, kp_scale, latency_ms}` so the sim rollout matches. This uses CMA-ES,
  or scipy `differential_evolution` when `cma` is missing.
  * **Proof without hardware:** a "hidden real" robot is the sim with secret parameters. Calibration recovers them
    within a stated tolerance from one or two probe motions (push, lift, swing).
* **Probe routine.** `{type: "calib", op: "probe"}` makes the robot run the probes in the current world and reports
  the fit (`state.calib`). In the real world this runs once per home: a new floor or table means a new friction
  estimate.
* **Real robot bridge (interface only).** `pps/bridge/` defines the `RobotDriver` protocol: `read_state`,
  `send_q_des`, `send_gripper` and `stop`. It includes a sim driver and a stub for LeRobot / ROS 2, so the same plans
  can drive hardware later. No hardware is claimed.

### P6 as built (details and results: `docs/calibration.md`)

* **Modules.** `pps/calib/{params,randomize,probes,log,sysid}.py`, `pps/bridge/{__init__,sim,stubs}.py`,
  `pps/features/calib.py` + `web/ui/calib.js`, agent tool `calibrate_here`, `scripts/calibrate.py`.
* **Plant changes (small).** `latency_ms` is a per-substep delay buffer (continuous, interpolated), not a per-tick one;
  two optional parameters `armature_scale`, `frictionloss_scale` (robot joints).
* **Probes.** swing (joint steps), press (force-limited guarded press), lift (weigh an object), slide (push an object
  across the table *while holding it*: free pushes jammed / tipped light objects in this contact model). Every command
  goes through a `RobotDriver`.
* **Fit.** Headless replay of the logged commands; joints + objects + wrist force compared as segment means; staged
  CMA-ES (own implementation, `cma` used when installed), 2 worker processes.
* **P1 interface.** `pps.calib.randomize.Randomizer(seed).sample()` → a `physics set` params dict (`.message(p)`),
  `.around(profile)` for site-specific ranges, lighting / texture hooks. Wired at integration: `scripts/generate.py
  --randomize physics` draws each episode's physics from it (one seeded randomizer per robot, its ranges) and stores
  the draw and the ranges in the episode metadata.
* **Safety (P5) at integration.** The probes move the arm at their own speeds (that is the measurement), so they start
  only at full safety speed and are aborted as soon as someone comes close (the runtime's own step, with the safety
  scaling and stop, takes over in the same tick). After probing the planner keeps clear of fixtures only.

## Demo packs (`pps/world/packs/`)

* **Weld cell.**
  * A table with two steel plates forming a seam, and a torch tool on the arm (UR5e or Panda) with its tip TCP.

## Rules for every workstream

* **Branching and PRs.** Branch from `v1/integration`, open a PR into `v1/integration`, and link the issue.
* **Self test.** `.venv/bin/python scripts/selftest.py` must stay green. Add a check in `scripts/checks/` for every
  feature.
* **Ports.** Each workstream gets its own range (below) and never touches 8777, 8443 or 8780.
* **Secrets.** Never print, log or commit `.env` or API keys. Tests use `--mock`/offline paths. Live LLM calls happen
  only in manual checks.
* **Resources.** The machine is short on RAM and disk:
  * run one server at a time;
  * close headless Chrome when done;
  * no large downloads (> 300 MB) without asking;
  * clean temp files.
